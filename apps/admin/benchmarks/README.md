# 性能基准与优化记录（2026-11-26）

测量分为离线固定数据和真实浏览器两组。先测量，再比较同一条链路；不把下载平台限流或随机视频的差异当成程序加速。

## 重复执行

在仓库根目录运行：

```sh
node apps/admin/benchmarks/catalog.ts > /private/tmp/catalog-performance.json
BENCH_WORKS=100000 BENCH_SAMPLES=20 node apps/admin/benchmarks/catalog.ts
.venv/bin/python apps/admin/benchmarks/browser.py --url http://127.0.0.1:3012
```

也可在 `apps/admin` 中执行 `npm run benchmark`。默认生成临时 SQLite 数据库：30,000 条作品、100 位作者，前24条实际创建小型媒体文件，其余用于衡量大目录索引、筛选及缺失文件处理。结束删除临时数据，不写真实资料库、不访问抖音。`before.json` 来自修改前 HEAD 的独立临时源码副本，`after.json` 来自当前工作树，使用同一版本脚本和 Node。常规场景每组12次，冷读1次、作品变化3次。记录 P50、P95、响应大小、事件循环最大延迟和进程结束时内存；内存不是峰值。

覆盖：冷启动索引、状态、作品分页、作者分页、作者作品、搜索、作品详情、媒体 Range、队列写入、作品写入和8请求并发。`summary` 是新增总数接口路径，旧代码返回普通列表；这里比较的是首屏为取得页数付出的代价。

真实 Chrome 测量用390×844移动视口，每次创建独立上下文，进行5次首播及每次3次方向键切换，记录长任务、API耗时、播放数和挂载媒体源数量。切换耗时含固定250ms观察等待，不能当作精确首帧延迟。`browser-before.json` 使用运行中的旧资料库，`browser-after.json` 使用独立新预览；视频随机且后台更新继续，因此结果只用于本机参考，不是严格的同视频A/B实验。

## 已定位并修改

- WAL/数据库文件变化原先总触发全库组装和跨线程复制。现在在工作线程读取浏览字段并计算签名；只有签名变化才发送新的完整索引，纯队列、重试状态写入沿用原索引。新增、改名、删除仍立即失效，没有加过期窗口。签名不变时仍需读取作品行，开销尚未归零。
- 随看推荐首屏先取页数，再取随机页；原先第一页12条媒体检查常被丢弃。新增 `summary=1`，保留原分页验证和筛选，返回总数与页数而不遍历媒体目录。
- 媒体返回 ETag/Last-Modified，匹配的 If-None-Match 在读取图片头或生成 HEIF 预览之前返回304；失效 If-Range 回落到完整响应。每次仍重新打开并检查真实路径和文件，保留外盘和文件替换检查。
- 管理页切页、搜索时取消上一轮列表请求，同时保留响应版本判断，减少过期响应争用。

## 第二轮：作品变化时增量刷新

生产读取路径改为复用工作线程。第一次读取建立完整快照；之后对数据库浏览字段逐行比较，仅重建受影响作者的作品、别名、搜索词、头像代表和计数，再向主线程传回这些作者的差异。主线程创建新的快照，已有请求持有的旧快照不被修改。作者迁移同时刷新原作者与新作者；数据库或媒体根目录切换、线程失败后重新读取完整快照。匿名作品采用一个保守分组，仍保证全量结果一致。

作者作品增加按作者分组的索引，作者页先取该作者的有序作品，再应用类型、来源和搜索条件。排序比较函数与完整重建共用，文件检查仍按当前页执行，没有引入文件结果过期缓存。

重复对比（无需下载器或抖音网络）：

```sh
python3 apps/admin/benchmarks/compare-incremental.py
```

脚本在临时源码副本中切回第一轮的单次线程/内容签名读取路径及全库作者筛选，随后串行运行当前实现；两版使用相同数据结构和基准脚本。普通场景36次，实际作品变化12次。结果是 `before-incremental.json` 与 `after-incremental.json`。它比较两种实现路径，并非切换到历史提交；不应把不同机器负载下第一轮的绝对数值直接合并。

| 场景 | 第一轮路径 P50 / P95（ms） | 增量路径 P50 / P95（ms） |
|---|---:|---:|
| 队列写入后读取 | 116.42 / 124.86 | 84.35 / 93.39 |
| 作品变化后读取 | 501.76 / 562.6 | 108.52 / 117.63 |
| 作者页 | 0.76 / 0.9 | 0.79 / 1.13 |
| 作者作品 | 2.38 / 3.5 | 0.37 / 0.43 |
| 详情 | 0.11 / 0.17 | 0.15 / 0.19 |
| 8请求并发整组 | 5.06 / 6.25 | 4.91 / 6.8 |

作品变化后读取中位数下降约78%，该阶段事件循环最大延迟 70.65 → 21.82 ms。详情页本轮没有代码改动，两版中位数均低于1ms；此前数毫秒的变化未稳定复现，不据此归因代码退化。

差异测试用完整重建作为参照，覆盖新增/删除、改名与别名、跨作者迁移、排序相同时间、头像、更改媒体路径、越界路径、匿名作品、空库及60轮混合编辑；同时检查旧快照不变、读取失败恢复、并发调用串行化和根目录切换。常驻线程空闲时 unref，不阻止程序退出，读取时仍保留30秒超时和错误恢复。

边界：数据库文件变化后仍需读取全库浏览字段；变化涉及一个拥有绝大多数作品的作者时，增量收益会降低。冷读仍为完整重建，主线程也仍需更新有序作品数组和查找映射；没有承诺所有负载都无长任务。真实外盘吞吐和平台限流未在本轮压测。

本轮检查还发现 `.venv/bin/python` 指向已经失效的 `/private/tmp` 解释器。已把同版本 Python 3.12.13 安装在忽略入库的 `.venv/.python-runtime/`，使用 `uv venv --allow-existing` 更新解释器链接，保留原有依赖；原 `pyvenv.cfg` 备份在 `.venv/pyvenv.cfg.before-runtime-fix`。此修复只影响本机虚拟环境，不改变项目Python版本要求。

本轮只用3011/3012独立预览验收，不替换正式3001服务；预览在验收后关闭。源码尚未提交或推送。

第二轮最终验收：资料库53/53、随看6/6、Python1396通过/1跳过，TypeScript、前端语法和Ruff通过。当前生产读取器在SQLite排他锁下也通过HTTP响应不阻塞测试。Chrome管理页预览/作者/搜索取消正常；移动与桌面播放器验收通过，包含触屏、收藏、进度、声音记忆和自动播放被拒后的恢复，页面错误为空。

## 第三轮：大作者只传回真正变化的作品

CPU采样定位到重复格式化/哈希、全作者对象组装和结构化克隆。第二轮虽然按作者分组，但同一作者有30,000条作品时，修改一个标题仍生成约26MB的差异对象。

现在复用未变化的数据库行、解析条目及作品对象，缓存失效由字段内容、作者名称/别名上下文和媒体根目录共同决定。主线程只替换变动作品和行，头像以作品ID关联回当前快照；旧快照保持不变。作者身份哈希及用于搜索的作者文本按作者计算一次。缓存只针对数据库元数据，文件与目录检查仍按请求执行。为避免额外遍历，字段比较与稳定行收集在同一轮完成。

新增离线分项基准：

```sh
BENCH_AUTHORS=1 node apps/admin/benchmarks/cold-and-dominant.ts
BENCH_AUTHORS=100 node apps/admin/benchmarks/cold-and-dominant.ts
```

每组30,000条作品、8次采样，比较本轮改动前的第二轮源码快照与当前实现；`dominant-*` 为单作者，`cold-*` 为100作者。标题更新的计时包含差异构建、结构化克隆和快照应用，不含SQL、HTTP或工作线程启动；差异JSON体积统计放在计时区间之外。不能把它当作完整API请求耗时。

| 离线场景 | 改动前 P50 / P95（ms） | 当前 P50 / P95（ms） |
|---|---:|---:|
| 同一作者30,000条，单条标题变化 | 337.18 / 523.18 | 77.68 / 96.1 |
| 100位作者，完整组装 | 185.84 / 207.28 | 138.45 / 167.96 |
| 100位作者，单条标题变化 | 44.21 / 63.11 | 50.46 / 65.31 |

大作者单条标题更新的差异JSON体积为26,177,589 → 1,289字节。100作者场景为262,663 → 1,287字节。大作者更新中位耗时下降约77%；普通小作者在此离线基准中有约6ms额外开销，不能宣称所有场景都提速。作者改名或别名变化仍可能需要替换该作者的全部作品。

完整API原始采样保存在 `api-compact-before.json` / `api-compact-after.json`；首次变慢的结果另存 `api-compact-initial-after.json`，交替A/B/A/B复测在 `api-compact-repeat-1..4.json`。普通API负载存在波动，部分采样变慢；尚未证明普通负载有全面收益，也没有把差异简单归因于机器负载。冷启动纯组装加快不等于端到端启动一定加快：首次读取、全量数据复制及内存成本仍存在。

新增测试检查5,000条同作者作品下只发送一条变化作品、旧媒体引用和快照不变，以及调用方原地修改行时正确失效。资料库55项、随看6项、TypeScript、前端语法及Ruff均通过。与改动前源码对照的30轮混合数据校验也通过（`compatibility-compact.json`）。Chrome管理页和移动/桌面播放器验收通过，无页面错误。

验收后确认3001未运行，已用当前版本启动正式资料库。实际读取29,232条作品、107位作者，首次状态请求2174ms；作品页、详情200、媒体Range206/1024字节及条件请求304均通过，更新状态为空闲。记录在 `live-compact.json`。3011/3012测试预览已关闭，3001保留运行。源码未提交、未推送。本轮未修改Python下载逻辑，沿用第二轮的完整Python回归结果。
